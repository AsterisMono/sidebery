# Plan 14 — SW-kill resilience audit of all bg services [M3]

> Part 14 of the Sidebery → Chromium MV3 migration.
> Master plan: `docs/migrate-plan.md` — read §5.2 "State resilience" bullets and §8
> (SW lifetime risk).
> Prerequisites: Plan 13 (persistence paths in place), Plan 7 (bg overlay +
> `docs/plans/notes-sw-state.md` initial findings).

## Goal

Audit EVERY `src/services/*.bg.ts` module for module-level mutable state that assumes
the background lives forever, and make each either rebuilt-on-init or persisted. This
completes milestone M3 (exit: tree/panels survive SW kill and full browser restart).

## Ground rules

No upstream `src/` edits — overlays (identical export shapes) or `patches/`.
Correctness must NOT depend on the SW staying alive (an open sidebar keeps it warm in
practice, but that's an optimization). **Commit after each completed TODO**
(`chromium: <summary>`). Firefox build/tests green.

## Method

For each bg service: list module-level `let`/`const`-mutable state; classify:
- **A — rebuilt by init**: repopulated by `main()`/its init from live browser state or
  storage → fine, verify the init actually runs on every SW start (Plan 7's overlay).
- **B — event-accumulated**: only written by event handlers after init → LOST on SW
  kill; needs persistence (`storage.session` for cheap/ephemeral, `storage.local` for
  must-survive-restart) or lazy rebuild on first use.
- **C — timers/debounces**: `setTimeout`/`setInterval` — dies with the SW; needs
  `chrome.alarms` (if ≥30s granularity ok), eager flush, or acceptance with rationale.
