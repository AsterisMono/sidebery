# Plan 8 — Side panel integration [M1]

> Part 8 of the Sidebery → Chromium MV3 migration.
> Master plan: `docs/migrate-plan.md` — read §5.1 (sidebar → `chrome.sidePanel`) and the
> `sidebarAction` rows of the §3 table.
> Prerequisites: Plans 4–7 (shim, adapters, env, SW background).

## Goal

Make the sidebar work as a Chrome side panel: action-click toggle, programmatic
open/close/toggle, `isOpen` detection, `_execute_action` keyboard toggle, and verified
sidebar window-identity/IPC.

## Ground rules

No upstream `src/` edits — overlays/patches only. Chrome ≥ 150 (gives
`sidePanel.open()` 116+, `close()` 141+, `onOpened`/`onClosed` 141/142+,
`runtime.getContexts()` 116+). **Commit after each completed TODO**
(`chromium: <summary>`). Firefox build/tests stay green.

## Context you need

- Manifest (Plan 2) already declares `side_panel.default_path: sidebar/sidebar.html` and
  the `sidePanel` permission.
- Upstream `sidebarAction` call sites (3 total per Appendix A of the master plan): grep
  `sidebarAction` under `src/`. Key one: `src/services/tabs.bg.ts` ~line 797 uses
  `sidebarAction.isOpen`.
- Sidebar window identity: the sidebar page resolves its window via
  `browser.windows.getCurrent()` + session window values; IPC uses a
  PortName-with-winId scheme (`src/services/ipc.ts`). `SIDE_PANEL` is a first-class
  extension context type, so `windows.getCurrent()` should work — this is the "verify
  early in M1" item.
- `sidePanel.open()` requires a user gesture (verified). Keybinding/menu/omnibox
  handlers count as gestures.

## TODOs

1. **Shim adapters for `browser.sidebarAction`** (replace Plan-4 warn-stubs in
   `src.chromium/platform/browser-shim.ts`):
   - `toggle()`: determine open state (see `isOpen` below) for the target window, then
     `chrome.sidePanel.open({ windowId })` or `chrome.sidePanel.close({ windowId })`.
     Accept the same argument shapes upstream passes (grep call sites).
   - `isOpen({ windowId })`: `chrome.runtime.getContexts({ contextTypes: ['SIDE_PANEL'],
     windowIds: [String(windowId)] })` → non-empty. Check the exact `windowIds` element
     type the API wants (string vs number) against real Chrome docs/types and normalize.
   - `open({ windowId })` / `close({ windowId })`: direct mapping.
   - `setTitle`/`getTitle`: no-ops (`setTitle` returns resolved promise; `getTitle`
     resolves the manifest default) — no per-window title API in `sidePanel`.
   - `setIcon`, `setBadgeText` etc.: no-op any that upstream calls (grep first; add only
     what's used).
   - Commit.

2. **Action-click behavior.**
   - In the bg overlay (`src.chromium/bg/background.ts` from Plan 7) init:
     `chrome.sidePanel.setPanelBehavior({ openPanelOnActionClick: true })` (verified:
     makes the action icon toggle the panel).
   - Find upstream's `browserAction.onClicked → sidebarAction.toggle` wiring (grep
     `browserAction.onClicked` / `action.onClicked` in bg services) and make sure the
     Chromium build doesn't double-toggle: with `openPanelOnActionClick` the browser
     handles the click itself. Neutralize the upstream listener in the overlay (comment
     with reasoning). The Firefox middle-click→options behavior is lost by design
     (Chrome gives no button info) — nothing to do here; the settings entry lives in the
     action context menu (Plan 15).
   - Commit.

3. **Keyboard toggle.**
   - `_execute_action` (added to the manifest in Plan 2, suggested `Ctrl+E`) performs the
     action click → opens the panel; it does NOT dispatch `commands.onCommand`
     (verified). Whether a second press closes the panel must be verified by a human in
     Chrome; prepare for the negative case: add a small commented-out (or
     config-guarded) fallback in the bg overlay that would bind a normal command to
     `sidePanel.close()` — and record this as an open verification item in
     `docs/plans/notes-verify-in-chrome.md` (create the file; Plans 8+ append to it).
   - Also grep upstream `onCommand` handling for `_execute_sidebar_action` references and
     make sure nothing breaks with that command absent.
   - Commit.

4. **Programmatic-open gesture audit.**
   - Find every path that calls `sidebarAction.open/toggle` (grep). Classify each as
     gesture-driven (keybinding, menu, omnibox, click) or not. Non-gesture call sites
     must tolerate `sidePanel.open()` rejecting — wrap the shim's `open()` in a
     try/catch that logs a warning instead of throwing upstream. List any non-gesture
     sites found in `notes-verify-in-chrome.md`.
   - Commit.

5. **Window identity / IPC verification support.**
   - Read `src/sidebar/sidebar.ts` init + `src/services/ipc.ts` port naming. Reason
     through the flow under `SIDE_PANEL` context; fix only what is demonstrably broken
     (e.g. if something assumes the sidebar page URL or a `sidebar_action` API).
   - Since real verification needs a human running Chrome, append a concrete manual test
     script to `notes-verify-in-chrome.md`: open panel in two windows → each shows its
     own window's tabs; create/close/move tabs → panel reacts; check SW console for IPC
     errors.
   - Commit.

6. **Verify builds.** `npm run build.chromium` + Firefox build/tests green. Commit fixes.

## Exit criteria

- Side-panel open/close/toggle/isOpen adapters implemented; action click and `Ctrl+E`
  wired; gesture constraints handled defensively.
- `docs/plans/notes-verify-in-chrome.md` exists with the M1 manual verification list
  (M1 exit: tabs panel renders and reacts to tab events — human-verified).
