# Plan 15 — Context menus: onClicked dispatcher [M4]

> Part 15 of the Sidebery → Chromium MV3 migration.
> Master plan: `docs/migrate-plan.md` — read §5.5 and the `menus` row of §3.
> Prerequisites: Plans 4 (shim throws on `create({onclick})`), 14 (init barrier).

## Goal

Rework background context menus for MV3: `CreateProperties.onclick` is unavailable in
service workers (verified) — replace with menu-id conventions plus one
`contextMenus.onClicked` dispatcher that works across SW cold starts.

## Ground rules

No upstream `src/` edits — overlays (identical export shapes) or `patches/`.
**Commit after each completed TODO** (`chromium: <summary>`). Firefox build/tests green.

## Context you need

- Custom in-sidebar DOM menus (the default and, after Plan 12, only mode) work as-is —
  this plan touches ONLY the browser-level menus created in bg.
- `onclick:` call sites (verified, 2 modules): `src/services/menu.bg.ts` (2 items — the
  action-button menu) and `src/services/tabs.bg.ts` `createOpenFromCacheMenu`
  (per-window "reopen cached window" items).
- Chrome persists created menus across SW restarts but errors on duplicate ids.
- Top-level items on the action menu are capped at 6 (`ACTION_MENU_TOP_LEVEL_LIMIT`);
  the current bg menu uses 3–4 — fits; multi-window reopen items already nest under one
  parent.

## TODOs

1. **Dispatcher module.** Create `src.chromium/platform/menus.bg.ts` (new file, not an
   overlay): registers ONE `chrome.contextMenus.onClicked.addListener` at module top
   level (SW-safe), awaiting the Plan-7 init barrier before dispatching. Dispatch by
   menu-item id string conventions — NOT in-memory closures — because the SW may
   cold-start between menu creation and click. Define the id scheme, e.g.
   `sidebery:open_settings`, `sidebery:reopen_cached_win:<index>`. Handlers resolve
   their target from the id + current state/storage. Commit.

2. **Overlay `menu.bg.ts`.** Read the upstream file. Recreate its action-button menu
   items via the dispatcher scheme: `contexts: ['action']` (verified valid), no `icons`
   property, no `onclick`. Creation guarded by `contextMenus.removeAll()` first (run
   during bg init — Chromium replacement for the FF `onHidden` cleanup). Include the
   "Open settings" item (this is the Plan-8 replacement for Firefox's
   middle-click-action shortcut). Keep the file's export shape. Commit.

3. **Overlay/patch `createOpenFromCacheMenu` in `tabs.bg.ts`.** `tabs.bg.ts` is huge and
   churny — prefer a patch swapping just this function's body, or a small overlay module
   the patch delegates to. Items get ids `sidebery:reopen_cached_win:<index>`; the
   dispatcher resolves index → cached window data from storage at click time (works
   after cold start). Nest under one parent item (cap compliance). Commit.

4. **Shim cleanup.** The Plan-4 shim throw on `menus.create({onclick})` should now be
   unreachable in the Chromium build — keep the throw (it guards future upstream code)
   but confirm via grep of the staged tree that no remaining call site passes `onclick`.
   Commit if changes needed.

5. **Verify.** Both builds green; Firefox tests pass. Append to
   `docs/plans/notes-verify-in-chrome.md`: right-click action icon → menu shows ≤6 top
   items, settings opens; with 2+ cached windows, reopen items work; kill SW, click a
   menu item immediately → still works; reload extension twice → no duplicate-id errors.
   Commit.

## Exit criteria

- No `onclick` menu usage in the Chromium build; single id-convention dispatcher
  survives cold starts; duplicate-id-safe creation.
